# chip2 — чувствительность детекции границы (для замены катушек), 2026-07-13

Задача: заменены приёмные катушки периметра на другой номинал (другая амплитуда сигнала) →
как перенастроить chip2, чтобы граница снова детектилась. Разобрано по декомпилу
`reverse-v2/chip2/decompiled_all.c` (два независимых прохода).

## Главный вывод (практический)

**Правильный фикс — аналоговый, на разъёме катушки, БЕЗ трогания прошивки.** Детектор жёстко
зашит на `|sample| > 2500` при авто-калибруемом DC-центре ~2048. Порог — flash-immediate, а chip2
гоняет IEC60730 FLASH-CRC32 self-test ⇒ патч прошивки требует пересчёта CRC, иначе плата упадёт в
self-fault. Поэтому: подогнать амплитуду сигнала новых катушек к тому, что ждёт прошивка
(усилитель/делитель на фронтенде), а не менять прошивку.

## Как принимается решение «волна есть» (сигнальный путь)

ADC+DMA → сырой буфер → раскладка в signed int16 по каналам (левый `+0x48`, правый `+0x68`),
окно `+0x92` = **800** (hi-res) или **235** (lo-res) сэмплов → ядро детектора `FUN_08015fa8`
@0x08015fa8 → покадровый компаратор амплитуды `FUN_0801baf8` @0x0801baf8 → zero-crossing
`FUN_08015dcc` (по знаку сэмпла — подтверждает, что сэмплы signed вокруг базы) → интегратор
площади/направления `FUN_08015260` → cJSON в chip1 (`FUN_08019914`).

Строка `left wave data error, area=%d, str=%d` @0x0801981c — это лишь sanity-проверка «знак площади
совпал с байтом направления», НЕ порог детекции.

## Ручки (ранжировано по применимости)

### ★ KNOB 1 — амплитудный порог (ЭТО и есть «чувствительность»)
`FUN_0801baf8` @0x0801baf8 (строки 16553–16589):
```c
sVar5 = 0x9c4;  sVar6 = -0x9c4;             // = ±2500 (ДЕФОЛТ)
if (param_5 == 1) { sVar5=5000; sVar6=-5000; } // "strong-signal" режим
... if ((2500 < sample) || (sample < -2500)) { keep; count++; } else zero;
if (param_3 < count) return 2;  // слишком много над порогом → «сатурация/помеха»
if (count < param_4) return 1;  // слишком мало → «волны нет»
return 0;                       // валидная волна
```
- Понизить 2500 → детектит более слабый сигнал (чувствительнее). Поднять → менее.
- **flash-immediate, рантаймом не пишется.**

### KNOB 2 — счётные гейты (сколько сэмплов окна должны превысить KNOB 1)
Аргументы в `FUN_0801baf8`: из `FUN_08015fa8` (стр.10407) `upper=600, lower=5`; суб-волна
`FUN_080164bc` @0x080164bc lower=5; `FUN_08016784` @0x08016784 lower=4.
- `count>600` → return 2 (помеха), `count<5` → return 1 (нет волны). Для слабых катушек меньше
  сэмплов проходят KNOB 1 ⇒ важен нижний гейт (5). Тоже flash-immediate.

### KNOB 3 — авто-де-сенситизация (флаг «strong», SRAM `+0xa8`)
`FUN_08015fa8` (стр.10440–10450): пока детектор возвращает «слишком много» (state 2), счётчик
`+0xa9` растёт; после `>20` защёлкивает `+0xa8=1` → порог KNOB 1 переключается 2500→5000.
- **Для слабых катушек этот флаг НИКОГДА не защёлкнется** (сигнал не «слишком сильный»), эффективный
  порог остаётся 2500. Т.е. дизайн центрирован на 2500; путь 5000 — против слишком сильного сигнала,
  нас не касается. Авто-повышения чувствительности для СЛАБОГО сигнала НЕТ.

### KNOB 4 — base voltage (DC-смещение) — АВТОКАЛИБРУЕТСЯ, это НЕ усиление
`FUN_08012b6c` @0x08012b6c (стр.6309–6366): усредняет 5 замеров ADC → `*_DAT_08012c88`. Валидатор
`FUN_0801a1f8` @0x0801a1f8: суммирует 8 конверсий, валидно если среднее в **[1906, 2191]**
(`0x772…0x88f`); вне окна — ошибка, подставляется дефолт **2048** (строка `base voltage =%d error,
set default 2048` @0x080174ef).
- Берётся **рантайм-замером**, не константа и не команда chip1. Самокалибруется к реальному DC-биасу
  приёмника. Сдвигает ноль, НЕ масштабирует амплитуду, зажат ~2048±140 ⇒ **как ручка чувствительности
  бесполезен.** (Подтверждает прежнюю заметку «2048 = mid-scale offset, не gain».)

### KNOB 5 — эффективный gain через аккумуляцию (объясняет число 2500)
12-битный ADC вокруг 2048 даёт ±2048, а порог 2500/5000 — значит сэмплы **аккумулированы** (не
одиночный raw−2048). `FUN_0801a1f8` суммирует 8 конверсий. Фактор аккумуляции окна живёт в HAL-объекте
ADC/DMA (`FUN_08019d34` @0x08019d34, vtable `+0x74`) — **точный immediate не выковырян** (индиректные
вызовы). Единственная незакрытая неоднозначность; всё остальное процитировано из декомпила.

### KNOB 6 — размер окна / период (вторично)
Окно `+0x92`=800/235; полупериод волны `+0x78`=`0x49b4`=18868 тиков (геометрия периода для
площади/направления, не амплитуда); допуски сегментов 20/25, зазор 50.

## Есть ли конфиг-канал с chip1? — НЕТ (второй агент, независимо)
chip1 → chip2 = только команды + `{"cmd":32772,"rtc":<сек>}` (синк времени). Единственный cJSON-строитель
в service_bdport.c (`FUN_0802244c` @0x0802244c) шлёт `cmd`+`rtc`. Ни base/threshold/gain/wave/area —
нигде. chip2 на приёме тоже не имеет команды «set sensitivity». **Путь «подстроить командой с главного
чипа» не существует в прошивке.** Тюнинг — только железо фронтенда или патч прошивки chip2.

## Ранжированный план под замену катушек
1. **★ Аналоговый фронтенд у разъёма катушки (предпочтительно).** Новые катушки слабее → поднять
   усиление (ОУ-каскад) до амплитуды старых; сильнее → делитель/аттенюатор. Прошивка не трогается,
   CRC/self-test целы. Целевая амплитуда: чтобы пиковые сэмплы уверенно превышали ±2500 при границе,
   но не давали >600 сэмплов над порогом (иначе трактуется как помеха).
2. **Патч KNOB 1 (0x9c4 → новое) в `FUN_0801baf8`** (+ при нужде гейты 600/5 и strong-режим 5000).
   Самый прямой, НО требует пересчёта IEC60730 FLASH-CRC32 и перепрошивки. Только если аналог невозможен.
3. base voltage (KNOB 4) — для амплитудной компенсации не годится (авто, зажат, это offset).

## Замер, чтобы выбрать множитель (без осцила): SWD в chip2
Читать signed-буферы каналов (левый `[obj]+0x48`, правый `+0x68`, `+0x92` сэмплов) при поднесении к
проводу периметра: старая уцелевшая катушка = эталон пикового |sample|, новая в той же позиции =
новый пик. Отношение = требуемый коэффициент фронтенда. Целимся, чтобы новый пик ≈ старому (уверенно >2500).

## Расхождение для проверки
Агент по SVD/memory_map определил chip2 как **GD32F30x_CL** (12-бит ADC, важно для арифметики выше),
тогда как `factory-map/06-chip2.md` пишет «GD32F4xx». Сверить по дампу; на выводы о ручках не влияет
(константы процитированы из кода напрямую).
