# 03 — FSM «КОСИТЬ» и «ДОМОЙ» + сервис движения (заводская chip1, GD32F4xx)

Ветка FSM: idle→departure→cutting и return/dock. Цель — найти, что завод делает при
СТАРТЕ ЕЗДЫ, что включало бы коммутируемый силовой рейл колёс «20U» и чего нет у нас
(нож крутится нашей fw, колёса лев+прав мертвы).

Источники: `chip1/decompiled_all.c`, `strings.txt`, `analysis/callgraph-chip1.tsv`, дамп
`dist/gd32-mainboard-dump-v1.bin`. Статус расследования: `reports/WHEELS-STATE-2026-07-08.md`.
Карта пинов: `reference/FACTORY-GPIO-PERIPHERAL-MAP.md`.

> ВАЖНО (архитектура): прошивка сервис-ориентированная (framework/service/*). Процессы FSM
> НЕ пишут регистры напрямую — они дёргают сервисы через **vtable** (косвенные вызовы
> `(**(obj+off))()`). Поэтому callgraph не видит рёбер к движению/мотору/BMS, а реальные
> записи в GPIO/TIMER/SPI спрятаны в методах драйверов. Ниже связки прослежены вручную.

## 2. ТАЙМЛАЙН «КОСИТЬ»: state3 → state4 → state5

### state3 (idle) — FUN_080270a8 (process_wait.c)
1. `FUN_08052d34()` — статус сенсоров/крышки → флаг +0x38.
2. `FUN_0804f758(...)` — **safety-check** (deal_safety.c). При ошибке — лог, остаёмся в idle.
   ⚠️ Здесь есть гейт «can not discharger» (см. §6): при защите пака завод НЕ трогается.
3. `FUN_0805deec()` — гейт расписания/старта (условие `+0x24==0 && +0x2c==1`).
4. `FUN_0805034c()+0x14` — border-service (периметр), НЕ силовой.
5. **Переход:** при готовности `FUN_0807976c(4)`.
   Логи: «auto departure delay time is reached, goto departure» @0x08027514,
   «Robot on schedule, start work» @0x0802756c.
   → НИКАКИХ записей в GPIO/TIMER/SPI при самом переходе. Только FSM-state.

### state4 (departure) — FUN_0803a7a0/FUN_0802fa90 → **FUN_08077e10(1)**
Реальный старт езды. FUN_08077e10(1):
- `*(mv+0x130)=1` (направление departure), флаги `+299=0xff`, `+0x145=0xff`.
- `FUN_0804e3e0()` — статус препятствия; выбор vtable-метода колёс (+0x7c или +0x84).
- **скорость** `uVar2=FUN_0804f2c8(0x3c,0x87)` (диапазон PWM ~0x3c..0x87).
- **КОМАНДА КОЛЁСАМ:** `(*pcVar6)(600, dir, speed)` — vtable движения (600=рампа мс).
- **«ENABLE»:** `(**(mv+0xc)+0xa8)()` — vtable-вызов «поехали» ПОСЛЕ задания скорости.
- Сброс счётчиков +0x4e/+0x12f/+0x158.

Куда ведут эти vtable-вызовы (movebase→драйвер), т.е. РЕАЛЬНОЕ ЖЕЛЕЗО:
- **TIMER2 (0x40000400)** CH2CV(+0x3c)=правое, CH3CV(+0x40)=левое — PWM-скважность.
- **A4963 направление** — SPI1 write `FUN_0801f4c6` → `FUN_0808408c` (`word|0x1000`).
- **Run/coast GPIO** — PD7 (лев, FUN_0805f3d8) / PD4 (прав, FUN_0806fc2c) через set/reset.
> Ни одного ОТДЕЛЬНОГО пина/регистра «rail-enable» сверх PWM+direction+run — НЕ обнаружено.

### state4 → state5 — FUN_08054274
- Условие `*(s+0x42) < *(s+0x40)` (пройдено departure-расстояние) → `FUN_0807976c(5)`.

### state5 (cutting) — FUN_0802fa90 → FUN_08077e10(3) + нож FUN_0802bce4
- Нож: vtable prepare(+0x54), enable(+0x34), `FUN_080784bc(speed)` (пишет `*(DAT_080784c4+8)`).
- Колёса: FUN_08077e10(3) — тот же путь (PWM+dir+run), плюс большой сброс cycle-счётчиков.

**Итог «косить»:** idle(safety/расписание) → FSM=4 → FUN_08077e10(1) [скорость+vtable enable] →
[движется: TIMER2 CHx PWM + A4963 dir SPI + PD7/PD4 run] → пройдено расстояние → FSM=5 → нож+циклы.

## 3. ТАЙМЛАЙН «ДОМОЙ» / ДОК

- Команда «домой»: FUN_080391e4 — по наличию границы ставит state 6/7/8 (`FUN_0807976c(6/7/8)`),
  затем `FUN_08078b18()` (сброс флага). Логи «dock command…».
- Возврат/движение к базе идёт тем же **movebase**-путём (FUN_08077e10 / FUN_08055f98):
  PWM CH2/CH3 + A4963 dir + PD7/PD4 run. Отдельного «rail»-действия нет.
- Дока/заряд — FUN_08025fd4 (process_charging.c), state 10. Здесь активируются **charge**-команды
  паку (into/exit charge, см. §6), но это ЗАРЯД, а не питание колёс.
- ⚠️ Полные тела process_docking_smooth.c / process_charging init (адреса 0x08085xxx) — ЗА пределами
  декомпила (файл кончается ~0x08085/строка 94394); детально не разобраны. Ограничение источника.

**Итог «домой»:** тот же движковый путь, что и «косить». Ничего нового для рейла 20U не найдено.

## 4. MOVEBASE — как движется (movebase_snk_v10.c)

- **FUN_08055f98** = «set path & go»: по типу станции (0..4) и направлению заполняет таблицу
  профилей скорости в объекте (off 0x2c..0x52: значения 8000..21000 мм/с·профили, 0x188..0x311 —
  ускорения), считает целевые дистанции `FUN_08079020` (мм→тики через wheel_perimeter/reduction),
  ставит `**(srv+4)=1` (running), `FUN_08078ee8(0)` (модель скорости 0). Порог `param_1>=0x20`.
- Скорость колёс задаётся НЕ напрямую в регистр, а как «модель» (FUN_08078ee8 case 0..4) + целевые
  профили; драйвер по PID/тахо (TIMER3) крутит PWM (TIMER2 CHx). Значение скважности приходит в
  CH2CV/CH3CV. Замер завода на ходу: ch2/ch3 0x681→0x1125 (force-capture) — это и есть выход movebase.
- При старте (FUN_08077e10) — vtable «enable» @+0xa8. Прослежен как «начать регулятор/подать PWM+run»,
  НЕ как отдельный power-gate.

**Вывод по movebase:** движок формирует профиль скорости → PWM + направление(SPI A4963) + run(PD7/PD4).
Никакого дополнительного пина/шины «включить рейл колёс» movebase не трогает.

## 5. КЛЮЧЕВОЙ КОД (аннотированный)

### A4963 SPI write+verify (FUN_0808408c) — единственный путь конфигурации мотор-чипа
```c
// param_2 = слово A4963; при записи выставляется WR-бит 0x1000; читаем назад, сверяем [11:0]
FUN_080840d8(dev, word);                 // CS↓; SPI1 TX (word|0x1000); CS↑
FUN_0806caac(dev, word&0xe000, &rd);     // чтение регистра (адрес в [15:13])
if ((word&0xfff) != (rd&0xffff)) retry;  // до 0x31 попыток, иначе -1
```
> У нас verify=0xFFFF даже у ЖИВОГО ножа ⇒ наш SPI1-READ не работает. Если у колёс A4963 (в отличие
> от ножа) POR-дефолт НЕ «RUN+вперёд», то незалетевшая SPI-конфигурация = стоящее колесо. См. §6.

### Левый мотор: направление (SPI) и run/coast (GPIO PD7)
```c
FUN_0805f300: FUN_0801f4c6(dev+0x28, cfg+0x30, dir);   // A4963 config бит1 (рег+0x0e) = направление
FUN_0805f3d8: FUN_080534f8/fc(GPIOD, 0x80);            // PD7 set/reset = run/coast
FUN_0806fc2c: FUN_080534f8/fc(GPIOD?, 0x10);           // PD4 = правый run/coast
```

### Старт движения (FUN_08077e10, departure)
```c
*(mv+0x130)=1;                            // направление
speed = FUN_0804f2c8(0x3c,0x87);          // PWM-скорость
(*pcVar6)(600, dir, speed);               // vtable движения колёс (рампа 600мс)
(**(mv+0xc)+0xa8)();                       // vtable "enable/поехали"  ← кандидат, но = регулятор+PWM+run
```

### BMS: enable-гейт команд паку (FUN_08072948)
```c
if (*(bms+0xa5)=='\x01') {                 // enable-флаг (ставится в FUN_08056980 из param_2[2])
  if (bits & 1)     (**(bms+0x20)+0x30)(); // send_cmd_into_charge
  if (bits<<0x1e<0) (**(bms+0x20)+0x34)(); // send_cmd_exit_charge
  ... +0x38 / +0x3c / +0x40                // прочие battery-state команды
}
```
> Это команды ЗАРЯДА (into/exit charge), не «включить разряд на мотор-рейл». Отдельной команды
> «enable discharge FET» в строках chip1 НЕТ (есть лишь discharge-ЗАЩИТА/мониторинг, §6).

## 6. ★ КАНДИДАТЫ НА ВКЛЮЧЕНИЕ РЕЙЛА 20U (ранжировано)

Firmware-путь движения (idle→departure→cutting и dock) НЕ содержит отдельного действия
«включить рейл колёс» сверх PWM(TIMER2 CHx) + направление(A4963 SPI) + run(PD7/PD4) — всё это
у нас уже воспроизведено (нож это подтвердил). Что остаётся:

### ★1. A4963 колёс требует SPI-конфигурации, а наш SPI1-READ/verify не работает (НОВЫЙ угол, firmware-тестируемо)
- ФАКТ: `FUN_0808408c` пишет config с verify; у нас verify=0xFFFF ⇒ **чтение SPI1 не работает**, а
  значит и запись могла НЕ примениться (или чип не отвечает).
- Нож крутится БЕЗ SPI (POR-дефолт ножевого A4963 = «крутиться»). НО у колёсных A4963 POR-дефолт
  направления/режима может быть иным (coast/standby) ⇒ без реально залетевшей SPI-конфигурации
  (слова 0x30..0x3e: reg0..reg7, вкл. `0xee0d`=reg7 RUN и `FUN_0801f4c6` направление) колесо стоит.
- ПРОВЕРИТЬ: починить SPI1 (CTL0/CTL1, MISO PB14, порядок бит/CPOL/CPHA) → добиться verify!=0xFFFF
  на КОЛЁСНЫХ A4963 → убедиться, что 7 слов конфигурации и направление реально записаны и сверены.
  Это единственный firmware-элемент старта езды, который у нас заведомо НЕ отработан (verify падает).

### ★2. BMS/пак: enable-флаг гейтит команды паку; движение может требовать активного линка/keep-alive
- `FUN_08056980` кладёт enable(param_2[2]) в +0xa5; `FUN_08072948` без enable==1 НЕ шлёт паку ничего.
- Найденные команды = charge (into/exit), НЕ явный «discharge FET on». Прямой строки
  «enable discharge output» в chip1 нет — вероятно, разрядный ключ пак держит сам (по wake/keep-alive).
- Согласуется с уже сделанным (keep-alive «держим мотор-VBB», connect `1C A1 03 C1 01 2E`): линк есть,
  но VBB колёс пока не поднялся. ДОРАБОТАТЬ: (а) слать enable=1 и периодику `FUN_08072948`-эквивалента;
  (б) искать в трафике завода на ходу кадр, которого нет у нас (SWD-снятие RAM пака/лог USART2 завода).
- Средний приоритет: пересекается с исчерпанным, но не закрыт байт-точно.

### ★3. Аппаратный high-side ключ рейла 20U (Q10/Q17/Q14)
- Если ни SPI-конфиг колёсного A4963, ни BMS не поднимают VBB — остаётся аппаратный гейт 20U,
  управляемый НЕ firmware-GPIO (по прошлым выводам). Прозвонить затвор Q10/Q17/Q14 завод-на-ходу vs наш.
- Низкий приоритет по решению пользователя (сначала прошивка), но это дефолтный исход, если ★1/★2 мимо.

### Снято/не подтверждено
- Отдельный «rail-enable» пин/регистр в FSM/movebase при старте езды — НЕ найден (перепроверено).
- vtable «enable» @+0xa8 (FUN_08077e10) — это запуск регулятора (PWM+run), не power-gate.
- BMS into/exit-charge — про ЗАРЯД, не про питание колёс.

## Ограничения
- process_docking_smooth.c / process_charging init (0x08085xxx) — за пределами декомпила.
