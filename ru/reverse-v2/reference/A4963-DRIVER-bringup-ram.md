# A4963 — bring-up, RAM-раскладка драйвера, адрес diag (chip1)

Дамп: `dist/gd32-mainboard-dump-v1.bin` (база 0x08000000, file_offset = addr − 0x08000000). Дизасм: `dist/factory-full.asm`. Каждый факт с меткой [V]/[I]/[U] и evidence (offset/asm-строка). Формат SPI-кадра A4963 (из `reports/drive-chain.md`, подтверждён): слово = `[15:13]=адрес рег(0..7) | [12]=W(ставится |0x1000 на отправке) | [11:0]=данные`. Верификация чтением: посылают `word & 0xE000` (адрес, W=0 ⇒ read), сравнивают `(word&0xFFF)==readback`.

## 1. Оркестратор bring-up

### 1.1 Верхний уровень — `FUN_080477c4` (`src/app/rw_init.c`) [V]
Порядок (по строкам ошибок в теле):
1. tilt-сенсор init; 2. battery init;
3. **BLADE** motor init: `(*puVar6[0])()` → err-строка `blade_motor_driver_init_failed` (rw_init.c:0x353), затем vtbl `[0x13]` (register/post);
4. **RIGHT** motor init: `(*puVar8[0])()` → `right_motor_driver_init_failed` (:0x362), vtbl `[0x13]`, при state==4 → `[0x15](0)`;
5. **LEFT** motor init: `(*puVar7[0])()` → `left_motor_driver_init_failed` (:0x371), vtbl `[0x13]`, при state==4 → `[0x15](0)`;
6. `(*puVar6[2])(); (*puVar7[2])(); (*puVar8[2])();` — общий пост-старт всех трёх.

Объекты-менеджеры берутся по типу платы: `FUN_0806e0b4`/`FUN_0806e79c`/`FUN_0806e4e4` (и ветки для др. board-type). vtbl[0] каждого = низкоуровневый a4963-init (`FUN_0805aee0` для LEFT и т.д.).

### 1.2 Низкоуровневый init (пример LEFT — `FUN_0805aee0`) [V]
Пошагово (decompiled_all.c:70008):
1. `malloc(0x48)` → объект; занулить поля, `byte[+0x22]=0xFF`, `byte[+0x18]=2`, `[+0x08]=1`, `[+0x10]=1`.
2. `FUN_08050578()`→`[+0x54]()` — прочитать вариант платы (0/2 vs 1/3) → выбрать набор reg-значений.
3. Заполнить теневые reg-слова в объекте (offsets 0x30..0x3e, см. §3) + указатели CS-функций в `[+0x28]`/`[+0x2c]`.
4. `FUN_0805f4ac()` — прочее.
5. **`FUN_0801f2f4(obj+0x28)` — HW-инициализация SPI1** (§1.3). Возврат 0 ⇒ дальше.
6. PWM/таймбейс: `FUN_0807f474/…(TIMER2=0x40000400,…)`, `FUN_0807f86c(TIMER3=0x40000800,…)` — каналы duty колеса.
7. `FUN_0801f4a8()` — PB12(NSS)→HIGH (idle).
8. **Отправка регистров A4963** циклом `FUN_0808408c(obj+0x28, *(obj+0x30..))`: reg0,reg1,reg2,reg3,reg4,reg5,**reg7** (offsets 0x30,0x32,0x34,0x36,0x38,0x3a,**0x3e**). **reg6 (0x3c) НЕ отправляется** [V] (asm 0x805afbe..; decompiled 70109-70118). Любой сбой → лог `a4963` + `A4963 init failed`.

### 1.3 SPI1 HW init — `FUN_0801f2f4` (init-once) [V]
- Флаг init-once: `if (*DAT_0801f424 == -1)` → `DAT_0801f424 = 0x20000580` (offset 0x1f424 = `20000580`). После init `*ptr='\0'` (0), mutex-хэндл в `*(0x20000584)`.
- SPI1 базa `DAT_0801f42c = 0x40003800` [V] (offset 0x1f42c).
- Пины SPI1 на **GPIOB** (`DAT_0801f428 = 0x40010c00`, offset 0x1f428): `FUN_08053558(GPIOB,0x10,3,0x1000)`=PB12, `…0x2000`=PB13(SCK), `…0x4000`=PB14(MISO), `…0x8000`=PB15(MOSI). `FUN_080534f8(GPIOB,0x1000)` = PB12→LOW (BC).
- **PB12 = аппаратный NSS SPI1, управляется софтом** (init: LOW; `FUN_0801f4a8` = `FUN_080534fc(GPIOB,0x1000)`=PB12→HIGH). ⚠️ Это НЕ «enable A4963» — выбор чипа делают per-chip CS (PD3/4/5). [V]
- TIMER2 (PWM опора) `DAT_0801f434 = 0x40000400` [V].

### 1.4 Где A4963 реально «крутит»
- **Разрешение драйвера = питание VBB + reg7 (RUN) при init.** Отдельного GPIO-enable A4963 в SPI-пути НЕТ [V] (единственные GPIO вокруг — CS PD3/4/5 и NSS PB12).
- **Момент движения:** duty PWM (TIMER2 CH) 0→N через `FUN_0807f696(...)` + направление/тормоз по reg7 через SPI. RUN уже взведён при init. Т.е. «крутящее состояние» = ненулевой duty при уже-RUN A4963, НЕ отдельная SPI-команда RUN на старте езды. [V] (см. §2, §4-drive)

## 2. reg7 / RUN — семантика и КОГДА пишется

**Значение reg7 у всех трёх драйверов = `0xEE0D`** [V]:
- BLADE @0x805a912 `strh r8,[r0,#54]` r8=0xEE0D (movw @0x805a8be).
- LEFT  @0x805afba `strh.w ip,[r0,#62]` ip=0xEE0D (movw @0x805af34); decompiled `*(iVar3+0x3e)=0xee0d`.
- RIGHT @0x805b8fa `strh.w ip,[r0,#62]` ip=0xEE0D (movw @0x805b874).

Все места записи слова с `[15:13]=111` (константа `0xEE0D`) в дампе: **только эти три init-функции** (`grep ee0d` → 0x805a8be/0x805af34/0x805b874). Отдельной константы reg7 при старте езды НЕТ. [V]

**Когда:** reg7=0xEE0D пишется **ОДИН РАЗ при init** (в общем цикле отправки reg0..reg7, последним) и держится. [V]

**Рантайм-правки reg7 (модифицируют ТОЛЬКО отдельные биты того же теневого слова reg7 = base+0x0e, затем ре-отправка):** [V]
- `FUN_0801f4c6(spi, regblk, …)` = **направление**: `regblk[+0xe] |= 2` (fwd) или `&= 0xFFFD` (rev) → бит1 reg7 = DIR. (строки `set_blade_direction_failed` и колёсные аналоги.)
- `FUN_0801f4b8(spi, regblk, …)` = **тормоз**: `regblk[+0xe] &= 0xFE0F` (обнуляет биты [8:4]) → «brake» (строка `set_blade_brake_failed`).

**Разрешение спора «RUN=1-с-init vs RUN-фронт»:** [V] → **RUN конфигурируется при init (0xEE0D) и держится**; при старте езды НЕ взводится SPI-фронтом. На старте меняются только: (а) duty PWM TIMER2 (0→N, это и есть «газ»), (б) бит1 DIR reg7, (в) биты[8:4] brake reg7. Отдельного «RUN=1» события на drive-time нет.

Декод `0xEE0D` (на отправке → `0xFE0D`): addr=7, W=1, data[11:0]=`0xE0D`. По рантайм-функциям: **бит1=DIR, биты[8:4]=brake-поле** [V]; точная привязка остальных бит к datasheet-полям (RUN/coast/restart/ESF) — [I], не докопано побитово.

## 3. RAM-раскладка объекта драйвера (теневые reg + указатели)

Общая схема (из init-функций §0):
- **BLADE** (64B): CS-функции в `obj+0x20`(assert)/`obj+0x24`(deassert); **reg-блок база = obj+0x28**, reg_k = base+2k ⇒ reg0..reg7 @ 0x28..0x36.
- **LEFT/RIGHT** (72B): CS-функции в `obj+0x28`(assert)/`obj+0x2c`(deassert); **reg-блок база = obj+0x30**, reg0..reg7 @ 0x30..0x3e.
- Общая формула теневого reg7 = **reg-блок база + 0x0E**.

Проверка адресов регистра по `[15:13]` — все совпали [V]:

| reg | BLADE (obj+) знач | LEFT var A / var B (obj+) знач | смысл (кратко) |
|---|---|---|---|
| reg0 | 0x28 = 0x03E4 | 0x30 = 0x03E8 / 0x01A8 | config0 |
| reg1 | 0x2A = 0x2A5F/0x2ADF | 0x32 = 0x22DF / 0x2ADF | config1 |
| reg2 | 0x2C = 0x478D | 0x34 = 0x4753 / 0x47D3 | config2 |
| reg3 | 0x2E = 0x6723 | 0x36 = 0x6721 | config3 |
| reg4 | 0x30 = 0x8974 | 0x38 = 0x8735 / 0x8745 | config4 |
| reg5 | 0x32 = 0xA933 | 0x3A = 0xA736 | config5 (slew/mode; правится `FUN_0801f4dc` биты[6:4]) |
| reg6 | 0x34 = 0xC000 | 0x3C = 0xC000 | **mask** — хранится, НЕ шлётся при init |
| reg7 | 0x36 = 0xEE0D | 0x3E = 0xEE0D | **RUN/DIR/brake** |

(BLADE evidence: strh-цепочка 0x805a8f2..0x805a912; LEFT: decompiled 70055-70085 + asm 0x805af72..0x805afba; RIGHT идентичен LEFT.)

Указатели CS-функций в объекте [V]:
- LEFT: `obj+0x28 = 0x0805fdc8` (assert=CS low), `obj+0x2c = 0x0805fdbc` (deassert=CS high) — литералы @0x805b12c/0x805b128.
- RIGHT: `obj+0x28 = 0x080705a4`, `obj+0x2c = 0x08070598` — @0x805ba70/0x805ba6c.
- BLADE: `obj+0x20 = 0x08022fd8`, `obj+0x24 = 0x08022fcc` — @0x805aa8c/0x805aa88.

Прочие поля init: `byte[+0x22]=0xFF` (LEFT/RIGHT) — состояние/«dir unknown» [I]; `byte[+0x18]=2`, `[+0x08]=1`, `[+0x10]=1`, `u32[+0x40]=0`, `u32[+0x44]=0` (LEFT). Флаг «инициализирован» как отдельное слово в объекте НЕ выделен; фактический «уже создан» = `*(глобал-указатель) != 0`. [V]

### 3.1 CS-функции (побайтово) [V]
Обе ветки бранчатся в общие GPIO-хелперы: assert→`0x080534f8` (`str r1,[r0,#0x14]`=**BC**, пин→LOW), deassert→`0x080534fc` (`str r1,[r0,#0x10]`=**BOP**, пин→HIGH). Порт во всех = `0x40011400`=**GPIOD**. Маски: LEFT `#32`=bit5=**PD5**, RIGHT `#16`=bit4=**PD4**, BLADE `#8`=bit3=**PD3** (asm 0x805fdbc/0x80705a4/0x8022fcc). CS активен-LOW.

## 4. ★ Адрес «последнего прочитанного diag» A4963

**Вывод [V]: заводской драйвер НЕ хранит diag-слово в постоянной RAM.** Единственный путь чтения MISO A4963 — верификация записи:
- `FUN_0808408c` (verify-write) → внутри `FUN_0806caac(spi, addr, &local_20)` кладёт 16-бит ответ в `*param_3`.
- В `FUN_0808408c` `param_3 = &local_20` — **стековая локальная**; после сравнения `(word&0xFFF)==(local_20&0xFFF)` слово отбрасывается. Старшие биты [15:12] (диагностика A4963) НЕ сохраняются. [V]
- `FUN_0806caac` — единственный вызов из `FUN_0808408c` (grep: 2 совпадения — определение + этот вызов). `FUN_0807dd92` (чтение `SPI_DATA` = base+0xC) вызывается только в verify-путях и в чужом SPI (`FUN_0806cc24`, другой периферии). Периодического health-poll A4963 с сохранением diag в объект/глобал — НЕ найдено. [V]/[U]

**Как всё-таки снять живой diag заводского драйвера (для калибровки нашего 0xFFFF):**
1. **[рекоменд.] Прочитать `SPI1_DATA` = `0x4000380C`** (SPI1 base 0x40003800 + 0x0C) — по SWD в момент/сразу после транзакции: там лежит последнее принятое 16-бит слово (старшие биты = diag A4963). [V-адрес, I-таймингозависимо]
2. **Брейкпойнт на возврате `FUN_0806caac`** (0x0806cb28 район) или на `*param_3=uVar3` — снять `local_20`/регистр с diag. [I]
3. Теневые reg-слова (§3) — читаются статически: показывают, что драйвер *отправил* (не что принял), но подтверждают, что init-конфиг дошёл в объект.

> ⚠️ Ключ: diag-калибровку делать через периферию SPI1_DATA / брейкпойнт, а не через «RAM-поле diag» — такого поля у заводского драйвера нет.
