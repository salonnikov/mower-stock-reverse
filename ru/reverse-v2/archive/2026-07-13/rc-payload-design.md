# RC-payload — дизайн ручного управления косилкой MI 302 (chip1 GD32F305)

Черновик v1, 2026-07-03. Всё опирается на подтверждённый реверс (`reverse-v2/`, `drive-chain.md`,
`SESSION-HANDOFF.md`). Цель: минимальная своя вставка в заводскую прошивку, дающая ручное RC-управление
колёсами, заливаемая по доказанному рецепту (payload в свободный флеш + пересчёт сквозного CRC).

**Легенда:** ✔C — доказано кодом дампа · ✔D — по даташиту A4963 · ⓗ — гипотеза/уточнить на стенде · ⛔ — риск.

---

## 0. Требования
- Ручной джог: вперёд/назад/поворот на вывешенных колёсах, по команде от хоста.
- **Fail-safe**: пропала связь/зависла команда → колёса встают (не «уехала сама»).
- Обратимость: откат на заводскую = восстановление флеша из `dist/gd32-mainboard-dump-v1.bin`.
- Не ломать штатную загрузку: любой байт в `0x08018000..0x080ffffc` требует пересчёта CRC → делаем всегда.

## 1. Точка hook — choke-point на писателях скорости колёс ✔C

Вся скорость колёс сходится в ДВЕ функции (подтверждено телами):
- `set_left_motor_speed`  = **`FUN_0805f620`** `(dir, |speed| 0..0x1c20-эквивалент)` → хвост `FUN_0805f300(dir)` + `FUN_0807f696(TIMER2,3,pwm)` → **CH3CV 0x40000440 (ЛЕВОЕ)**.
- `set_right_motor_speed` = **`FUN_0806fe66`** зеркало → `FUN_0806fb54(dir)` + `FUN_0807f696(TIMER2,2,pwm)` → **CH2CV 0x4000043c (ПРАВОЕ)**.

Все пути привода (border-cycle state5/6, прямая инъекция `FUN_0803b6f4` в state1/7/8, heading-контроллер)
в итоге зовут именно эти две функции. Значит **патч ПРОЛОГА `FUN_0805f620` и `FUN_0806fe66`** =
универсальная точка перехвата.

**Почему это снимает проблему гонки 10мс** (из прошлой сессии SWD-запись проигрывала контуру):
мы не пишем CH3CV снаружи и не деремся раз-в-секунду. Мы стоим ВНУТРИ того же вызова, которым контур
каждые 10мс задаёт скорость. Когда FSM зовёт `set_left(fsm_dir, fsm_speed)`, наш пролог СРАЗУ подменяет
аргументы на `(rc_dir, rc_speed)` до тела — контур физически не успевает записать своё, мы заменили его
намерение в единственном чокпоинте. Гонки нет by design.

### Механика патча (trampoline / veneer)
Пролог функции нельзя переписать «на месте» (не хватит места под нашу логику). Классика:
1. В свободном флеше (0x08090000-регион) кладём **veneer** для каждой из двух функций.
2. В прологе оригинала первые N байт (кратно инструкции, ≥4 для `LDR PC,[PC,#..]`/`B.W`) заменяем на
   переход в veneer.
3. Veneer: читает mailbox → если RC активен и «свежий», подменяет `r0=rc_dir, r1=rc_speed` → исполняет
   **вытесненные** оригинальные инструкции → возвращается на `orig+N` и дальше идёт штатное тело (gear-map,
   SPI-DIR, CH3CV). Если RC неактивен — просто выполняет вытесненные инструкции и возвращается (no-op).

⚠️ Точные байты пролога и размер вытеснения определяются на РЕАЛЬНОМ дизассемблере фрагмента
(`objdump`/Ghidra по адресам 0x0805f620 и 0x0806fe66) на этапе имплементации — по декомпилу их не взять.
Нужно учесть литеральные пулы и то, что `param_1/param_2` приходят в `r0/r1` (AAPCS).

## 2. Активация привода (энергизация A4963/драйверов)

Драйвер колеса живёт ТОЛЬКО в ходовом состоянии: `FUN_0805aee0` (левый create+energize, 608 б, объект
`_DAT_0805b09c`; `*_DAT_0805b09c==0` ⇒ не создан) malloc-ит объект, шлёт 8 SPI-слов A4963 (reg7=`0xee0d`,
RUN=1) и конфигурит TIMER2 CH3. В idle (state 3) не вызывается → CH3CV не крутит, наш пролог-хук не
срабатывает (функцию никто не зовёт). Значит RC-джог из idle требует, чтобы привод был запитан.

**Вариант A (v1, форс состояния) — ❌ ПРОВЕРЕН ЖИВЬЁМ 2026-07-03, НЕ ГОДИТСЯ.**
Форс `state 0x200000bc=4`: FSM мгновенно ушёл 4→**5 (cutting)**, драйверы поднялись, **оба колеса поехали
ВПЕРЁД, CH3=CH2=0x681** (~1-2с) — энергизация и езда работают. НО через ~1-2с FSM сам свалился в **error 9
(дисплей E11)**, CH→0x48≈0, колёса встали. Т.е. форс ходового состояния НЕ УДЕРЖИВАЕТСЯ: FSM детектит
несоответствие (нет реального cutting-контекста/сенсоров) и аварийно останавливается. Даже удержание state
каждый тик не спасёт — переход в error происходит внутри FSM-логики. **Вывод: v1-активация форсом state
отброшена.** (E11 латчится в UI отдельно; SWD `state=3` останавливает привод, но не гасит E11 — нужен
power-cycle/ack.)

**Вариант A' (форс не-cutting состояний) — ❌ ТОЖЕ ПРОВЕРЕН И ОТБРОШЕН 2026-07-03.**
Форс 1/2/8 → мгновенный отскок в idle(3), привод НЕ поднимается. Форс 7(dock) → error9 (дисплей E5).
Форс 6(findborder) → сразу error9, держится в ошибке, привод 0. Итог: форс ЛЮБОГО ходового (4/5/6)
самоаварийно валится (FSM видит отсутствие нав.контекста), не-ходовые (1/2/7/8) привод не энергизируют.
Форс state как активация RC МЁРТВ полностью. (В прошлой сессии state6 вёл колёса лишь потому, что туда
переводила НАСТОЯЩАЯ команда «домой», готовящая контекст, — не голый форс переменной.)

⇒ **ЕДИНСТВЕННЫЙ путь активации = Вариант B (v2): payload сам зовёт `FUN_0805aee0` (+ правый),
держа FSM в idle.** Валидируется только сборкой+заливкой (вызов по SWD без halt на poll.cfg небезопасен).

**Вариант B (v2, цель): энергизировать самим.**
Payload напрямую зовёт `FUN_0805aee0` (+ зеркало правого) для создания/энергизации драйверов, минуя FSM,
и держит state в «нейтрали» (например idle, где FSM не рулит колёсами). Тогда никакой борьбы с автопилотом.
⛔ Зависит от глобалов/мьютекса/gear-детекта (`FUN_08050578`), требует стендовой проверки, что вызов вне
FSM-контекста безопасен. Уточнить на железе.

Рекомендация (ОБНОВЛЕНО после стенда): форс cutting-состояний отброшен → идём в **v2 (прямая энергизация
`FUN_0805aee0`)** ЛИБО v1' (форс state 1/7/8, проверить). Энергизация+езда как механизм подтверждены
(при форсе state колёса реально крутились 0x681 — подтв. пользователем 2026-07-04).
⚠️ ОПРОВЕРГНУТО (2026-07-04): наш изолированный вызов `FUN_0805aee0` из hook колесо НЕ крутит (CH3CV пишется, но нет RUN) — энергизация FSM ≠ одиночный FUN_0805aee0. Разбор реального пути энергизации в работе.

## 3. Mailbox (канал команда→payload)

### Структура (предложение, 16 байт)
| off | тип   | поле        | смысл                                                   |
|-----|-------|-------------|---------------------------------------------------------|
| 0x0 | u32   | magic       | 0x52434D31 ('RCM1') — payload игнорит мусор/непрошитое  |
| 0x4 | u8    | rc_active   | 1=RC рулит, 0=отдать FSM                                 |
| 0x5 | u8    | left_dir    | 0=вперёд 1=назад                                        |
| 0x6 | u8    | right_dir   | 0/1                                                     |
| 0x7 | u8    | reserved    |                                                         |
| 0x8 | u16   | left_speed  | |скорость| в единицах аргумента set_left (0..~0x1800)   |
| 0xa | u16   | right_speed | то же для правого                                       |
| 0xc | u32   | heartbeat   | хост инкрементит каждую посылку; payload следит за ростом|

### Fail-safe watchdog ✔ (обязательно)
Payload на каждом тике сравнивает `heartbeat` с предыдущим. Не растёт `>=K` тиков (напр. K=50 ≈ 0.5с) →
принудительно `rc_active=0` и скорость 0 (BRK=1 удерживает). Это защита от обрыва SWD/зависшего хоста.

### Где разместить mailbox
- **Рекоменд. для v1 (стенд, SWD-транспорт): фикс-слово в SRAM. ✅ ПОДТВЕРЖДЕНО ЖИВЬЁМ 2026-07-03.**
  Записал сентинелы `0xCAFE..` в 0x20010000/0x20014000/0x20016000, прогнал косилку через энергизацию+езду+error
  — **все три пережили нетронутыми** (heap НЕ дорос до них даже при создании драйверов). Свободная «дырка»
  SRAM ≈ **0x20010000..0x20016xxx** (в idle нули; статические глобалы ниже 0x20010000, стек-краска сверху
  от ~0x20017800). **РЕКОМЕНД. АДРЕС mailbox = `0x20014000`** (середина дырки, макс. запас и от heap снизу,
  и от стека сверху). Запись в SRAM по SWD работает всегда (не зависит от клоков).
- **BKP data-регистры `0x40006c00..` — НЕ для v1.** В декомпиле 0 ссылок на BKP/PMU-clock ⇒ приложение почти
  наверняка НЕ включает клок backup-домена ⇒ запись BKP заблокирована до `RCU_APB1EN|=PMU,BKPI` + `PMU_CTL.BKPWEN`.
  Это ломает простой openocd-poke хостом. BKP оправдан только в беспроводном v2 (нужна персистентность и
  payload сам включит домен). ⓗ

### Транспорт команды (кто пишет mailbox)
- **v1 (стенд): SWD-mailbox.** Хост через openocd (`mww`) пишет поля + инкремент heartbeat. Едет по нашему
  уже готовому SWD-тету (`:4444`), никакого нового протокола. Идеально для первого теста на вывешенных колёсах.
- **v2 (беспровод): своя категория `0x31` в диспетчере команд `FUN_080470f0`** (свободный слот рядом с
  `0x30→FUN_08044c80`) → хендлер пишет mailbox. Тогда RC идёт по штатной радиосвязи телефон-косилка. Больше
  интеграции, отдельная задача.

## 4. Размещение payload и CRC
- Код veneer'ов + логика: **`0x08090000..`** (свободно ~450К, всё 0xFF, вне кода приложения ~до 0x08090000).
- После записи payload + патч-байтов пролога: пересчитать сквозной HW-CRC-32 (poly `0x04C11DB7`,
  init `0xFFFFFFFF`, слова LE, MSB-first, без реверса/финXOR) над `0x08018000..0x080ffffc` и записать в
  **`0x080ffffc`**. Стоковый CRC = `0x0f69a878`. Метод записи bank1 — как в `flash_proof.cfg` (PG один раз
  на страницу + mwh + sleep), доказан end-to-end.
- ✔ **Готовый тул CRC: `tools/bench/app_crc.py`** (host-side, в контейнере). ПОДТВЕРЖДЁН: на дампе v1 даёт
  ровно `0x0f69a878` = хранимому слову. Пересчитать/записать: `app_crc.py <образ.bin> --set` → `<образ>.crcfixed`.
- ⛔ Патч пролога попадает в bank0 (`0x0805f620`/`0x0806fe66` < 0x08080000) — писать в bank0 через штатный
  stm32f1x нельзя без стирания страницы (страница занята кодом). Нужно: **стереть страницу с этой функцией и
  переписать её целиком с изменённым прологом** (сохранив остальное тело), ЛИБО искать способ program-only.
  Это тоньше, чем payload в чистый bank1 — детально проработать в имплементации (кандидат: собрать патч как
  «переписать 1-2 страницы bank0, где лежат обе set_* функции», + payload в bank1 + CRC). Оценить, что обе
  функции в пределах немногих страниц.

## 7. Подтверждённый дизасм прологов + точный рецепт патча ✔C (capstone по дампу v1)

Дизассемблировал `dist/gd32-mainboard-dump-v1.bin` (Thumb, capstone в контейнере). Итоги:

- **set_left вход = `0x0805f620`** (4-байт выровнен). Первая инструкция:
  `2d e9 f3 4f` = `push.w {r0,r1,r4,r5,r6,r7,r8,sb,sl,fp,lr}` (32-бит, 4 байта).
- ⚠️ **ПОПРАВКА К ПАМЯТИ: set_right вход = `0x0806fe6c`, НЕ `0x0806fe66`/`0x0806fe67`.**
  Пред. функция кончается `bx r1` @0x0806fe64; далее 6 байт паддинга (`0000 7405 0020`) до 4-байт границы;
  настоящий пролог `push.w {r0,r1,r4,r5,r6,r7,r8,sb,sl,fp,lr}` (тот же `2de9f34f`) стоит на **`0x0806fe6c`**.
- Оба входа: (1) 4-байт выровнены; (2) первая инструкция ровно 4 байта → **чистая 1:1 замена на `B.W veneer`**
  (тоже 4 байта), без разрезания инструкции; (3) `push.w` сохраняет r0(param_1=dir) и r1(param_2=|speed|)
  на стек; (4) далее идёт `ldr r0,[pc,#..]` (PC-relative — НЕ вытесняем, остаётся на месте, на orig+4).
- `B.W` из обоих прологов достаёт до payload 0x08090000 (дистанции 0x309e0 и 0x2019a << ±16МБ). ✔

### Рецепт veneer (стратегия «override r0/r1 ДО push»)
Подменяем входные параметры в r0/r1 в самом начале, ПЕРЕД штатным push — тогда и регистровые, и стековые
копии параметров = наши RC-значения, и функция ведёт себя так, будто её позвали с нашими (dir,speed).

Патч входа (обе функции): `push.w{...}` (4 б) → `B.W veneer_{L,R}`.

```
veneer_L:                         ; r0=dir, r1=|speed| от caller (FSM)
    push  {r2, r3}                ; сохранить скретч
    ldr   r2, =MAILBOX            ; литерал в veneer
    ldrb  r3, [r2, #4]            ; rc_active
    cbz   r3, .pass               ; RC выкл → проброс без изменений
    ; watchdog: сравнить [r2,#0xc]=heartbeat с сохранённым last_hb в RAM-скретче mailbox+0x10;
    ; если stale>=K → r1=0 (стоп, BRK удержит), иначе:
    ldrb  r0, [r2, #5]            ; left_dir  → param_1
    ldrh  r1, [r2, #8]            ; left_speed→ param_2
.pass:
    pop   {r2, r3}
    push.w {r0,r1,r4,r5,r6,r7,r8,sb,sl,fp,lr}   ; ВЫТЕСНЕННЫЙ оригинальный пролог (с нашими r0/r1)
    b.w   0x0805f624             ; вернуться на orig+4
```
Для set_right: mailbox off `0x6`(right_dir)/`0xa`(right_speed), возврат `b.w 0x0806fe70`. Точную аллокацию
скретч-регистров (r12/magic-проверка) финализировать при ассемблировании; критичные факты (4-байт push-вход,
params в r0/r1, override-до-push) — подтверждены.

### Патч-страницы bank0 (перезапись)
- set_left: страница **`0x0805F000..0x0805F7FF`** (2КБ). set_right: **`0x0806F800..0x0806FFFF`** (2КБ). Разные.
- Процедура: считать обе страницы из дампа, поменять 4 байта входа (`2de9f34f`→`B.W`), стереть+перезаписать
  каждую страницу целиком штатным bank0-программатором (stm32f1x, размер флеша ЯВНО 0x100000). Payload/veneer'ы
  и их литералы — в bank1 `0x08090000` (лёгкая запись). Затем пересчёт сквозного CRC → `0x080ffffc`.
- ⛔ Итог заливки трогает bank0 (2 стирания) + bank1 (payload) + CRC-слово. Каждое стирание bank0 = окно
  brick-риска → держать питание, всё detached, откат-дамп наготове.

## 6. Итоговая рекомендация (v1, минимальный рабочий RC)
1. Mailbox = подтверждённое на стенде свободное SRAM-слово, заполняется по SWD (`mww`) с heartbeat (BKP — только v2).
2. Veneer-патч пролога `FUN_0805f620`+`FUN_0806fe66`: при `rc_active`&свежем heartbeat → подмена (dir,speed).
3. Активация: payload держит `state=4` пока `rc_active` (v1); watchdog по heartbeat → стоп.
4. Payload+CRC заливаются по доказанному рецепту; откат = восстановление дампа.
5. Тест ТОЛЬКО на вывешенных колёсах, нож физически отключён, косилка на питании (не дать уйти в
   авто-выключение посреди записи — brick-риск).
